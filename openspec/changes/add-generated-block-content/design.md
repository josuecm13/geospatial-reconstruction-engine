## Context

Milestone 10 gives every area one stored ground grid, and Milestones 9 and earlier give it blocks with
buildable areas and roads. Generation reads both and writes only to its own tables. The rules are
recorded in `docs/architecture.md` ("Generated block content"); this document records only the
decisions behind them. See proposal.md, Why.

## Goals / Non-Goals

**Goals:**
- A run is reproducible from its seed, its stored fingerprints and its feedback, and can be explained later.
- Generated buildings never overlap real ones, stand on the stored ground, and stay out of excluded land.
- A person's correction of a block is honoured on the next run, without rewriting what OSM says.

**Non-Goals:**
- Machine learning, or any model fitted beyond the area's own observed buildings.
- Authentication. The feedback and generation endpoints are open, as the rest of the API is.
- Writing to any observed table, or changing ingestion, reconcile or the terrain grid.

## Decisions

- **Eligibility is a pure rule, checked in a fixed order.** A block is built on only when it is whole
  and has room: not clipped, not a median, and a buildable area of at least 30 m², and the first reason
  wins. Only the area's own blocks are eligible, so composed inner areas are generated by their own runs.
- **Suitability subtracts named reasons, each with its own zone.** Water (buffered 20 m), steep ground
  (over 30%, only with a stored grid) and non-residential land use are subtracted from the buildable
  area, and each leaves a zone so it can be shown. A single blanket exclusion of all constrained land was
  rejected, because it would hide why a block is empty.
- **Style is read from the roads, not from building coverage.** `informal` needs low water nearby and the
  grid, so it is never chosen without elevation. `sparse` is decided by road length per square kilometre
  of land within 500 m of the block centroid, not by building coverage: OSM maps roads far more completely
  than buildings, so coverage would call an under-mapped town rural.
- **References come from fully built frontages.** The frontage is the exterior of the buildable area, and
  each real building is measured against its nearest edge. A block is an exemplar only at 0.70 or more
  frontage coverage with three or more buildings, so its fingerprint describes a built street rather than
  a few stray houses.
- **Matching is local and scored.** Candidates are exemplars within 500 m, in any completed area. The score
  adds distance, road-class mismatch, size ratio and style mismatch, with the block id as the tie-break, so
  the choice is deterministic. Defaults by bounding road class apply when nothing matches, so every block
  gets an answer.
- **Determinism comes from per-block seeds in sorted order.** Each block's RNG is seeded from the run seed
  and the block id, and blocks and edges are walked in sorted order, so iteration order never changes the
  result. The fingerprints used are stored with the run so it can be explained later.
- **Feedback is a maximum count or a refusal.** A stated count caps the run: the generator takes an evenly
  spaced subset of the lots that fit, and reports a shortfall when the frontage cannot hold that many.
  "No buildings" generates nothing. Feedback is calibrated across similar blocks (same style) within 500 m,
  by the ratio of their feedback counts to their previous generated counts, clamped to 0.5 to 2.0.
- **Feedback keeps no foreign key on purpose.** A block id may belong to a block that a re-import removed;
  the feedback must survive so it can be reported as orphaned rather than silently applied elsewhere.
- **Stored runs, with staleness computed on read.** One run per area, replaced in one transaction. Deleting a
  block cascades its generated buildings, so a re-import that sweeps a block leaves the run stale rather than
  wrong. Staleness compares the road-graph hash and the grid version at read time, so nothing has to be told
  when roads or terrain change.
- **Layering keeps the rules testable without a database.** The rules (eligibility, fingerprint maths,
  matching, seeded sampling) are pure in `app/domain/generation.py`. The geometry in local metres is in
  `app/generation/` with shapely, and the database binding sits on top.

## Risks / Trade-offs

- **Generated buildings are plausible, not measured.** → Mitigation: the generated colour and the Show
  generated toggle keep them visibly apart from measured buildings, and each carries its style and its
  reference block.
- **Calibration can move a neighbour's lots.** → Mitigation: it only divides the lot width by a ratio
  clamped to 0.5 to 2.0, and only with at least two similar blocks nearby.
- **A re-import that removes a block orphans its feedback.** → Mitigation: orphaned feedback is listed and
  never applied to another block.
- **Unauthenticated write endpoints.** → Accepted for this milestone, as the rest of the API is open.
  Authentication is a separate decision, not part of this change.

## Migration Plan

- One Alembic migration adds the land-use enum values, and one adds the generation tables and the settings
  table. Both are additive; existing areas have no run until Generate is pressed.
- Rollback drops the new tables and leaves observed data untouched.
